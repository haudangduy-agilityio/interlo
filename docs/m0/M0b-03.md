# M0b-03: Bundle size, idle memory and sockets of the desktop shell

Recorded 2026-11-23 by `scripts/check.sh app`. The raw files are in `docs/m0/M0b-01/evidence/` (text only); every number below is quoted from one of them. The shell is the React shell only (D-191): the window, the sidebar and the screens with sample or empty data. No audio, no engine and no model is loaded, so these numbers are a floor for the app, not an estimate of it. Memory has no target (it is a baseline); a target is set after the numbers exist.

## Sockets (AC-4)

Three launches, one sample every second for 60 s each (180 samples). Each sample lists the app process, its children and the web view helper processes that appeared after the launch (GPU, networking and web content: four pids per launch), and runs `lsof -nP -a -p <pids> -i -F pPn`. The rule: every address is loopback and there is no wildcard listener. Results, from `03-sockets-launch1.log` to `03-sockets-launch3.log`:

```text
RESULT: 60 samples in 60 s (0 late by more than 1 s), pids 68365,68379,68380,68381, sockets seen: 0, no wildcard listener and no non-loopback address
RESULT: 60 samples in 60 s (0 late by more than 1 s), pids 72275,72304,72305,72306, sockets seen: 0, no wildcard listener and no non-loopback address
RESULT: 60 samples in 60 s (0 late by more than 1 s), pids 77113,77145,77146,77147, sockets seen: 0, no wildcard listener and no non-loopback address
```

The check can fail: `05-negative-controls.txt` shows it refusing real test listeners bound to `0.0.0.0` and `[::]` and accepting one bound to `127.0.0.1`, and `lsof` stderr output fails the step.

What it cannot see (from `03-limits.txt`):
- A connection that opens and closes between two 1 s samples.
- DNS lookups done for the app by a system daemon, network work done for the app by another process, and Unix-domain sockets (`lsof -i` lists internet sockets only).
- It is the app idle on its first screen for 60 s, three launches: evidence about the app process tree and its web view helpers while idle, not a proof that nothing leaves the Mac, and not a reading during a meeting.
- A helper process that another app starts during the run is counted too, and one that exists before the launch is not (the web view helpers have the parent process 1, so the parent cannot say which app they serve).

## Interrupted launches (not hidden)

One launch ended by itself: `03-interrupted-launches.log` has `RESULT: launch 3, try 1: the app process ended before the readings were complete (2026-11-23T10:27:37+0700)`, and `03-sockets-launch3-try1-interrupted.log` shows the app process gone at sample 4 (4 s after the launch). The launch was repeated and the repeat is launch 3 above. Earlier runs on 2026-11-20 and 2026-11-23 ended early the same way. The cause was not found: there is no crash report, and the app binary run directly for 90 s stayed alive with no output. It may be another process on the machine closing the app. Until the cause is known, this is a stated limit of the run, not a finding about the app.

## Reproduce

`scripts/check.sh app` rebuilds this folder (about five minutes; it needs an unlocked screen and Screen Recording for the app that runs it). A second reader can run it and compare: the pass lines must repeat, and the memory numbers vary, so compare the median and the spread.

## What this does not show

- Memory with a live meeting, a model or an audio route: those come with M0b-05 and later tasks.
- Memory of the web view helper processes.
