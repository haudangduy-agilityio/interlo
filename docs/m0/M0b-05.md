# M0b-05: Core Audio process tap spike

Task M0b-05 of FT-02. Code: `bench/M0b-05/` (own `[workspace]`, D-190). Evidence: `docs/m0/M0b-05/evidence/`
(raw logs, `SUMMARY.md`, `SHA256SUMS`). Platform: macOS 26.4.1 on a Mac mini (Mac16,11), Apple silicon.
macOS 14.4, the platform floor (FR-42), was **not tested** (SPEC O-15).

## Answer

A process tap on one chosen app works from a Rust crate with four exact-pin bindings crates, on this Mac.
With the tap on one browser instance, the level meter moved with the test clip (AC-11), the tap did not hear
the spike's own tone (AC-12), a tone from a second browser instance, another app and a notification sound did
not reach it (AC-13, AC-14), and it fell back to the 2-channel virtual device in the cases that D-15 names
(AC-17, AC-20, AC-40) and refused only when no route was left (AC-36). The two checks that need something this
Mac does not have are listed below as BLOCKED or as a deviation. The plan for M1-06, M1-34 and M1-50 can go ahead
as planned, with the five findings in "What the spike found" kept in mind.

## What the spike is

- `bench/M0b-05/src/`: `levels.rs` (RMS and 1 kHz Goertzel level over 100 ms windows, medians, energy mean),
  `route.rs` (D-15 decision table), `monitor.rs` (idle floor, Silent rule, silence fill), `targets.rs` (which pids
  belong to the target), `analysis.rs` (offline checks over a run log), `ca.rs` and `capture.rs` (Core Audio, the
  `unsafe` part), `spike.rs` (the run). 92 unit tests: `bench/M0b-05/check.sh`. The root gate does not build `bench/`.
- It prints one `<epoch ms> <event>` line per event and one `WIN` line per 100 ms window (levels only). It writes no
  audio: AC-21, and the ring between the callback and the main thread holds levels, never samples.
- The target app is the set of processes whose command line holds a given argument (and their descendants): the
  browser instance with its own temporary profile (`--target-arg --user-data-dir=...`). Its process objects go into
  `CATapDescription initStereoMixdownOfProcesses`, an include list; this process is never in it (AC-12).
- Reproduce: `bench/M0b-05/bundle.sh`, then
  `M0B05_BROWSER=<browser app path> bench/M0b-05/harness/evidence.sh <out-dir>` (every step in the order of the
  SPEC) and `... evidence.sh <out-dir> grant ac16r ac18r` for the repeated timings, then
  `bench/M0b-05/harness/summarize.py <out-dir>`. The steps `grant` and `deny` reset the spike's own permission and
  wait for its system dialog to be answered (Allow, then Don't Allow); they were answered by a mouse click through
  an accessibility tool, never by a key event. The output volume, the output sample rate, the browser windows and
  their temporary profiles are put back when the script ends, also after a signal; the spike's own audio-capture and microphone permissions are reset to "not decided" (not restored to a granted state).

## What the spike found

1. **Permission attaches to the bundle only when it starts through `open`.** A binary started from a shell is
   judged as the terminal app. The spike is a signed local bundle (`app.interlo.bench.m0b05`, usage descriptions in
   `Info.plist`); `run.sh` starts it with `open`. A rebuilt bundle kept its permission (same local identity).
2. **There is no public call to ask the audio-capture permission state.** The spike uses the private
   `TCCAccessPreflight` (`ca.rs`), which also keeps answering with its first result inside a long-running process;
   so each look is a short-lived child of the same bundle. Without that call the spike cannot tell "refused" from "silent".
   The product needs a decision before M1-06: another way to know (for example the dialog result), or this call
   with its risk accepted. Not decided here.
3. **A browser stops its audio output stream when it has been silent for about 30 s, and its helper processes
   exit.** The tap then delivers no callbacks at all. The spike treats no callbacks as digital silence (`synth=1`
   windows, 181 of them in `03-ac13/app-spike.log`), which is what makes `IDLE_FLOOR` and `SILENT` work. The tap
   list is fixed when the tap is made, so the spike looks the target's process objects up again every second and
   restarts the tap when the set changes (`RETARGET`). That path was **not** exercised in the final evidence run
   (no `RETARGET` line in any log); it is covered by code review only. M1-06 must plan for a target that creates or
   restarts its audio process after the tap started.
4. **The 2-channel route needs the microphone permission**, a second system dialog for the same bundle. It was
   already answered when the 2-channel checks ran.
5. **Restart after a sample rate change is fast**: 84 ms median (see AC-18). The aggregate device clocks from the
   default output device, so a change on that device is the one that matters.

## Deviations from the SPEC

- **AC-19 source.** The SPEC routes the browser's output to the 2-channel device. Listing the output devices in a
  web page needs the browser's microphone permission, which the owner did not authorise for this task, so the
  browser was not routed. The check proves that the spike captures from the 2-channel device and reports `route=2ch`;
  it does not prove the browser routing. The owner decides whether AC-19 counts as PASS or stays open.
- **AC-13, other browser instance.** The SPEC says the default browser profile. The owner's rule is that the daily
  profile is never used, so a second instance with its own temporary profile played the tone. The point of A-8 (a
  separate browser instance has its own audio process) holds.
- **AC-17 permission state.** Reached by answering the system dialog with "Don't Allow" after
  `tccutil reset AudioCapture app.interlo.bench.m0b05`, not by toggling a setting in System Settings.
- **`evidence.sh` changed after the run** only to replace the home directory and the per-user temporary folder in
  the text logs, to add the repeat steps, and to harden the cleanup after the second review (mute state, microphone
  reset, pid checks); the committed logs were edited with the same replacements. The spike binary and its code are the ones of the run
  (`00-meta/meta.txt`: `binary_sha256`).
- **Code after the run.** Since the commit of the run (`ddc254a`, `00-meta/meta.txt`) only test code of the spike
  changed (96 unit tests now; `git diff ddc254a -- bench/M0b-05/src` has hunks inside `#[cfg(test)]` modules only).
- **Starting guesses added by the assistant** (the SPEC gives none): a bucket of one second needs 8 of 10 windows,
  a 10 s period needs 95 of 100, and a status or tone check may miss 5 windows (`analysis.rs`).

## What the checks miss

- **AC-11, 13, 14, 35:** they read levels, so they prove that the tap carries the browser's sound and does not
  carry the other sounds that played. They do not prove that nothing else could ever get in: the test sounds were a
  synthetic speech clip, a 1 kHz tone and one notification sound, on headphones as the output device. A leak of
  another kind (another frequency, a longer sound) is not tested. The idle floor was digital silence (-120 dBFS)
  every time, so any leak that played during the period would show.
- **AC-12:** the spike's tone was played on the default output device only, and the tap held an include list. A
  tap built with the "everything except" constructor was not tried; the control run puts this process into the
  list on purpose and then hears the tone.
- **AC-16, 18:** timings over five runs on one Mac. 44.1 kHz was the only other rate tried, on the headphone output.
- **AC-17, 20, 36, 40:** they read printed lines and the exit code. The level on the 2-channel route is AC-19's job.
- **AC-21:** it scans for audio file names and files over 1 MB in the spike's folders. It cannot see a file written
  elsewhere, or raw bytes inside a text log (the logs are small and hold only numbers).
- **AC-39:** `lsof` sampled once a second on the spike's own pid. A connection shorter than a second, a connection of
  a helper the spike starts (`ps`, its own child that reads the permission), and the browser's own traffic are not seen.
  A run that ends within a second is sampled once.
- **The test sources** were synthetic. A real meeting with a second person (H-14) and desktop meeting app A, whose
  helper processes play the sound (D-168), were **not** tested.

## Known gaps (found in review, not fixed)

- The retarget path (`RETARGET`) was never exercised by a run. A rate-change restart with no fresh process object
  reuses the old object ids; whether Core Audio reuses an id for another process is not known.
- The target matcher uses `ps` words: an argument with spaces is split, and a wrapper process that carries the
  marker is selected with its children. In this evidence none of these had a process object. The product capture
  (M1-06) must record the root executable instead.
- The check that the aggregate device holds only the tap's input channels fails closed, but was not tried with an
  output device that has a microphone (a headset).
- The unit tests do not cover the capture callbacks (`unsafe`, hardware); the evidence runs do.

## Notes for later runs

The logs here come from synthetic sounds. A run with a real meeting (H-14) would put the speech-activity timeline of real people into the `WIN` lines: keep those logs out of the repository and commit only the verdict lines.
