## Answer

On a native full-screen window, a panel made only with Tauri window flags is **not on screen**: the window
exists, but the window list shows no window of the spike on the current Space, and the screenshot shows no panel
(AC-24 NO). A native non-activating panel (`NSPanel`, `NonactivatingPanel`, collection behaviour
`CanJoinAllSpaces | FullScreenAuxiliary | Stationary`, solid colour) shows over the same window, stays 60 s, lets
a click through to the page when click-through is on, catches the click when it is off, and does not change the
frontmost application or the key window over 20 show and hide transitions. So the plan for the caption overlay
(M1 tasks that need FR-40 and FR-25) takes mechanism 2, the native panel. Four checks need a second display;
the owner decided on 2026-11-25 to run them on one display only, so they are NOT RUN (see the table). Two things about the native panel were found on the way and are listed under
"What the spike found".

## NO results: cause and change to the plan (AC-34)

- **AC-24 and AC-25 with Tauri flags.** Cause: the Tauri window is created with always-on-top and "visible on all
  workspaces", but not with the full-screen auxiliary collection behaviour; a native full-screen window lives on its own
  Space and the flagged window is not on it (`onscreen=[]`). Proposed change: the caption overlay uses the native
  panel (mechanism 2). A third option is not tested: a Tauri window whose native window gets the collection behaviour
  set through its handle. It is an extension spike if the team prefers one window type (D-167); this spike did not
  run it.
- **AC-23 with the native panel, no prime.** Cause: not isolated. The data: the spike started before the test
  window and had no window on screen; at its first show the frontmost application became the spike
  (`own_active=1`) and stayed so for that snapshot; after a prime (a transparent show and hide at start-up, before the
  browser starts) the same show left the focus alone, and 20 later transitions never moved it in either sitting. Most
  likely a freshly launched application takes the focus when its first window is ordered front. Proposed change: none
  for the product if the product shows the panel from a running application (the main window already exists); the
  panel code must not be the first window of a launch. This is a reading of two sittings, one run each.

## What the spike found

1. The Tauri window flags alone do not show a panel over a native full-screen window on this Mac (AC-24 NO).
2. The first window of a freshly launched application takes the focus (AC-23, native, no prime). Avoid it by not
   making the panel the first window, or by a transparent prime as the spike's `--prime` option does.
3. The native panel's window level reads layer 3 (floating) in the window list, not the status level the code
   asks for. Most likely `setFloatingPanel(true)`, which runs after `setLevel(25)`, resets it; the spike did not swap the
   calls to prove it. The panel showed over the full-screen window at layer 3, so the collection behaviour is the likely
   reason it is visible there.
4. Colour of a screenshot: `screencapture` writes the display's colour profile; a nominal #E6007E read (203,44,111) in a
   dry run, and the converted copy read (229,2,126); these dry-run values are not in a committed log. The pixel check
   reads a copy converted to sRGB (`sips --matchTo`).
   The original file is the one that is hashed and shown.
5. The sitting is paced by a person. The first version of the harness counted a click outside the yellow square as
   the click of the step, and counted page clicks after the control window had ended. Both are fixed
   (`TDD-LOG.md` slice 5, kept outside git); sitting 1 is the run that showed them, and its raw files are kept.

## What the checks miss

- The pixel check proves that the panel colour covers the rectangle at two instants; it does not prove the panel
  stays there between them.
- AC-23 compares the frontmost application and its topmost layer-0 window, not the true key window; a key typed
  during the run and logged by the page is the only direct proof, and it is one key.
- AC-31 samples `lsof` for the spike's own pid each second; the web view helper processes of the flags panel are
  other pids and are not in it (SPEC gap G-5).
- One sitting per row: a different Space layout, another display, an older macOS (FR-42 floor 14.4) or the real
  meeting application (O-8 extra run) were not tried; the extra run is NOT RUN.
