## Answer

All four models load in process from Rust, each in its own process, and each printed a plausible first output
for the test sentence `vi_001` of `docs/m0/reading-list.md`. The voice output, recognized by the recognition
model, gave back 14 of the 15 words of the input sentence. No model needed a helper process, so the default of
D-14 (runtime in the app process) holds for these four files on this Mac.

## Results

`BENCH` is `bench/M1-35/target/release/m1-35`, built with `cargo build --release`. Peak memory is the
`maximum resident set size` of `/usr/bin/time -l` on the measured process, in decimal MB (bytes divided by
1000000). Load time is the time to create every session of the role. First-output time is the time from the
loaded models to the finished first output: the whole sentence for translation, all frames plus the codec and
the resampling for voice, the speech audio plus one second of silence for voice activity detection, features
plus decode for speech recognition. It is not time to first audio. Work minutes are the assistant's own
estimate, not a measured timer. One run per row. An earlier run of the same logic (commit `7e4e2d7`, before
the review fixes) gave 1408, 13425, 25 and 3250 ms load and 1658, 3233, 50 and 2897 MB peak memory for the
same four rows, so the numbers move by tens of percent between runs on this Mac (the data volume was nearly
full and swapping during both).

## What the spike found

1. **Peak memory is far above the file sizes.** Translation needs about 1655 MB for 404 MB of files, and
   voice about 2700 to 3200 MB for 903 MB. These are the peaks of separate processes. They do not add up to the peak of one
   process that holds all four, and no run here loaded all four together. M1-42 and M0-09 measure that.
2. **Voice load time is 13 to 19 s.** Three graphs and the codec load from cold. A product that starts the voice
   model at app start must hide this, or load it in the background.
3. **The voice model is built for Vietnamese.** Its card says it is not an English voice and is not
   evaluated as one. This spike ran the Vietnamese test sentence through a preset voice. English speech from
   the same model, which the English-voice row of `docs/m0/candidates.md` assumes, is **not checked here**;
   M0-07 (listening) covers it.
4. **The preset voice needs no voice encoder.** A voice is a stored array of 10 by 768 values. The file
   `voice_encoder.onnx` of the list was not downloaded, because the reference code does not call it. The files
   `decode_step.onnx`, `null_voice_emb.npy` and `silence_frame.npy` were downloaded as listed and are unused
   by this spike.
5. **The codec graph names its weight file in its own metadata.** The download list uses a shorter name, so
   the `voice` role reads the stored name from the graph and makes a hard link with that name inside the
   ignored models folder, once. If a file with that name already exists it must be the same file, or the
   role fails.
6. **The translation tokenizer file declares a normalizer entry with no character map**, which the tokenizer
   crate rejects with a panic. The role drops that entry before it loads the file. The test sentence is in
   composed form, so the ids do not change; a sentence that needs the dropped normalization could differ.
7. **The merged decoders run without a cache here.** Each step runs the whole prefix with empty past tensors.
   The 88 ms and 1197 ms first-output times include that cost; a cached loop in M1-36 and M1-38 is expected to
   be faster, which this spike did not measure.

## What these checks do not prove

The pass rules prove that each model loads and produces a plausible first output for one sentence. They do not
prove accuracy (word error is M0-05), latency of the chain (M0-09), behavior in a long meeting, or that the
community files equal the official weights. The recognition share of 0.933 is one sentence and one run.
AC-13 checks audio file extensions only, and AC-14 checks a word list only; the review covers the rest.
